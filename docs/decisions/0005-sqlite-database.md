# 0005：SQLite 与受保护的 Schema 迁移

- 状态：参考；阶段 00 设计记录，rusqlite 集成和迁移探针待验证。
- 影响范围：Kenvoy 持久化、连接生命周期、迁移引擎。

## 背景

基础应用应由 Kenvoy 独立启动，不要求额外数据库服务；数据需要在重启、构建和部署后保留。

## 问题

SQLite 是同步数据库接口，需要避免阻塞 Tokio 工作线程；源码变化也不能成为删除旧数据的授权。

## 可选方案

1. 内存数据：不能满足持久化验收。
2. 外部数据库服务或 JavaScript 数据层：增加部署要求，并违背当前默认路线。
3. rusqlite 访问独立持久化 SQLite 文件，自定义 Schema Diff 与迁移管理。

## 最终选择

采用方案 3，默认项目根目录下 `data/app.sqlite`，与 `dist` 分离。开发和生产解析相同路径规则。候选连接方案为专用数据库工作线程持有连接，通过有界任务队列访问，先串行化写操作；不把 `Connection` 无约束共享到异步任务。rusqlite 的 `Connection` 标记为 `Send` 而非 `Sync`，同步调用不应直接占用 Tokio 核心调度线程。[Connection API](https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html)

连接初始化显式设置并核对 Foreign Keys、WAL 和 Busy Timeout；事务失败回滚。WAL 可以改善读写并行，但仍有单写入者和忙锁条件，不是无限并发保证；数据库部署在本机持久化文件系统。[SQLite WAL](https://www.sqlite.org/wal.html)

迁移先生成 Diff，记录版本、校验值、计划和实际执行结果。仅经过分类验证的安全变更可按模式策略自动应用；删除、类型变化、约束收紧和可能重命名不能仅根据名称猜测后执行。删除 JSX 字段保留数据；破坏性计划必须另行明确确认。

## 原因

满足本机启动与真实持久化，连接所有权清晰，并将源码声明与数据修改授权分开。

## 已知缺点

单工作线程存在吞吐上限；WAL、备份、长事务和迁移锁需要专项测试。SQLite 的表修改能力不等于安全迁移策略。

## 影响

所有 SQL 标识符来自验证后的 Resource IR，值使用绑定参数。内部表不注册为公开资源。迁移前后检查实际 Schema；数据库状态与记录不一致时阻止启动或更新并报告原因。

## 验证与状态

本轮未引入 rusqlite，也未创建数据库。阶段 04 必须用临时文件验证新增、重复迁移、约束变化检测、失败回滚、真实重启持久化和并发忙锁；随后验证 HTTP 层不会阻塞运行时。
