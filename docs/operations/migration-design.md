# 迁移执行协议

状态：参考（现状文档）；已实现 Schema Diff、只读预览、安全应用、确认与一致性备份。数据库连接和字段映射见 [数据库设计](../architecture/database-design.md)。

1. 将 ApplicationIR 转为规范 SchemaModel，去除标签和源码位置，复核标识符、类型、默认值与约束。
2. 读取迁移历史和规范快照；对照 sqlite_master 中的实际受管对象与元数据，发现漂移停止执行。
3. 生成 MigrationPlan，包含 from_version、前后 Schema hash、实际结构 hash、数据库绝对路径、变化清单与 checksum。
4. 新表、兼容增列和预检通过的索引可安全应用。删除、类型/约束变化等需要当前完整 checksum；过期或错误确认拒绝。
5. 破坏性操作先使用 SQLite backup API 保存一致性备份，再在事务中重新核验并执行。复制 WAL 主文件不能代替备份。
6. DDL、数据复制和版本历史同事务提交；失败回滚。成功后才允许激活新业务模型。

候选改名只报告可能的旧、新字段，不自动推断；首版即使有确认也拒绝改名执行，尚无用户映射接口。新增必填字段无有效默认值而已有数据时，必须阻断；确认不会跳过数据有效性检查。

`migrate status` 和 `history` 使用只读路径，不因不存在数据库而创建文件。`history` 不依赖源码能否解析，故障时仍可查看。重复应用相同模型不增加迁移版本，标签调整不触发数据库重建。

系统组件重载不改变 Schema。select 的 when 和远程来源筛选属于运行校验，单独变更不产生 DDL、不清理已有数据；静态枚举全集仍是物理约束，静态/远程切换须按 Diff 验证。既有记录与新规则不一致时保留原数据，在后续提交时返回校验错误。

认证固定表由独立 Schema owner 核验。未知内部表、附加认证 trigger/index 或版本漂移不会因 `_kenvoy_` 前缀而被放行。业务 API 的资源注册表进一步阻止访问这些表。

恢复时先停止写入，保留原数据库、WAL/SHM 和失败日志，确认备份是完整的 SQLite backup 成果。首版没有自动恢复命令，不能把未完成备份文件当作可用恢复点；人工恢复应针对具体数据库和后果确认，且不得直接覆盖用户数据。

已验证初始化、索引冲突、约束变化、事务中 FK 失败、删除确认、过期 checksum、AUTOINCREMENT 高水位和持久化；磁盘满、进程断电与极大数据集性能不属于现有实测覆盖。命令和证据见 [阶段 04 验证](../verification/0006-sqlite-runtime.md)。
